how fourier packs compute

every step of inference, which chip runs it, and how the work is packed so nothing waits that doesn't have to.

what runs today, checked against the code on 2026-11-24: mel and search on the cpu, the encoder and the decoder on the gpu, on macos and on ios and ipados. the neural engine encoder exists but lost on exactness, so it runs only when pinned. the packing diagrams further down show the design, and say where today differs. numbers are on the performance page.

the whole path

the gpu runs the encoder, the prefill and every decoder step. the cpu runs the audio stages, the search and the text. the neural engine has an encoder path that is used only when a caller pins it. the main thread only draws.

the combined engine

the design: one wide decoder batch on the fastest chip, the encoder working ahead on another, and the cpu running beam logic. x, y and z are audio pieces, a number is a decoder step, and each row of a piece is a beam. a column is one turn in order, not a timing.

the encoder is drawn on the npu as the plan drew it. the race went to the gpu: today a new piece is encoded and read in on the gpu between decoder steps, one piece per step while others run. the batch, the slot refill and the beam logic on the cpu are as drawn.

how calls get packed

  1. store 16-bit, compute 32-bit. weights are read at half the memory cost, and the math keeps full precision.
  2. one wide decoder batch. beams and pieces share each weight read.
  3. refill slots at once. when a piece ends, the next one takes its slot without draining the batch.
  4. encoder works ahead. not today: with the encoder on the gpu, a new piece is encoded between decoder steps.
  5. never copy beam history. each step writes to its own cache slot, and a per-beam ancestry table says which slots make up each beam.
  6. batching must be invisible. a row's scores are bit-identical at any batch width, slot, neighbor or padding, with metal fast-math off.
  7. pack the calls. a decoder step for every running piece is one gpu command buffer. the engine can also read several waiting pieces in one prefill, bit-identical to reading each alone, but the scheduler does not use it: a try showed no gain for twelve clips at once.
  8. slow down, never overflow. bounded queues hold back the stage before a slow one.
  9. fail loudly, retry once. a work buffer that cannot be made throws instead of switching kernels. a file piece whose gpu call fails runs once more, and a live phrase whose exact pass fails is tried once more before its live text stands in.

what it reads

audio length, queue, deadlines, measured step time, memory pressure, thermal state, power, and chip health.

what it changes

batch width, which pieces share a step, priority, and the piece length for long audio. it does not move a stage to another chip.

what it never changes

the answer. only exact paths are eligible, at any batch width and any load.

where the bits are fixed

batching must be invisible: a row's scores must not change with how many rows share a call or where the row sits. this holds in two different ways. the source is the header of Sources/FourierKit/Model/Kernels.swift.

pathused forwhy a row's bits hold
the project's metal kernelsevery decoder step, at any batch widtheach output value is computed in a fixed order that depends only on that row's data and context. most values come from one thread. rms norm, softmax and the value mix split into runs of 64 that add their partial sums in a fixed order. the one-row and three-row bandwidth kernels add in the same order and are bit-identical. a decoder step never uses apple's kernel. metal fast math is off.
apple's matrix kernel (MPSMatrixMultiplication)the prefill and the encoder, for products of 32 rows or more, and square prefill attentionits order is apple's and not documented. measured on the m4 against a 6,400-row run, a row's bits stop depending on the row count and position once the count passes a boundary that grows with the inner width: 10 rows at 1,024 and 2,048, 30 at 6,144, 40 at 4,096, 90 at 4,320 and 75 at 7,680. below it apple's kernel takes another path. so these passes are a pure function of the piece, and pieces read in one product stay identical to being read alone only when each is past the boundary by itself.

the encoder's conv front runs in groups of 1-second chunks of 208 rows or more each, past the boundary, and the projection out of it runs once over the whole clip. so the encoder's result no longer depends on the conv group a device derives. weights stay as the checkpoint's bf16 bits and are widened to 32-bit inside each kernel, or one matrix at a time for apple's kernel, which is exact. the golden test checks the decoder side at total widths 1, 2, 3, 4, 5, 7, 8, 10, 11 and 12. the matrix-kernel boundaries were measured on an m4 only.

text while it works

all three modes show text before they finish. the host calls back after every decoder step with the tokens so far. listen turns them into a draft that grows token by token. record runs quick greedy passes over the audio so far, cutting at a quiet point past 20 s so a pass never grows with the recording. transcribe streams the finished pieces as settled and the leading beam of the running one as a draft. with beams, that draft can change wholesale until its piece ends. progress inside a piece moves with the encoder, the prefill and each step, against an estimate of about 3.6 tokens per second of speech. only the transcript each mode returns is exact.

six ways to pack

the engine combines these. each one is a bet the hill-climb can keep or drop.

the decoder's ceiling

the plan's estimate, from an early read test of about 91 gb/s on the m4, below the chip's 120 gb/s spec: the fastest a 2-minute clip could decode from weight reads alone. the cost depends on how weights are stored, so 32-bit math can still run at the 16-bit ceiling. measured since: the bandwidth kernel reads about 86 gb/s alone in a microbenchmark, and the layer matrices inside a real step about 77 gb/s (2.82 gb in 36.7 ms). one clip decodes at 19.9 to 21.8 steps per second, against a ceiling near 26 with a short context and near 20 with a long one.

a wide batch does not make one clip faster than this. it lets several clips share the same weight reads, so total throughput rises until compute or cache traffic becomes the limit.

the exact path keeps a 32-bit cache, about 229 kb per context token, or about 0.46 gb per step for a 2-minute piece. this is why long audio prefers shorter pieces. the clip also spends an estimated 2-5 s in prefill plus the encoder, so the 4-6x estimate is closer to a best case.

what decides a placement

  1. it is exact. it passes the golden test on all three clips, or it is out.
  2. it wins the task's number. throughput, speed or latency.
  3. on a tie, the npu wins. a tie is within 3%. no neural engine path has passed rule 1 yet.

build order

  1. run the one-layer benchmark. done. the bandwidth kernel on raw bf16 weights won the step, and apple's kernel won many-row products.
  2. build the full 32-bit path with batched beams. done, and it passed the golden test on its first complete run.
  3. add the beam ancestry cache, so beam history is never copied. done.
  4. switch to 16-bit weights with 32-bit math and cache. done: weights are read as stored and widened in the kernel.
  5. widen the batch and refill its slots. done, up to 12 rows, with the three-row kernel.
  6. race the encoder on the npu and gpu. done: the gpu won on exactness, and working ahead was not built.
  7. test pure 16-bit math. the neural engine encoder failed the margin. not tried for the decoder.
  8. turn on the scheduler. done, with limits derived from the device. reading pieces in groups is built in the engine and not used.
