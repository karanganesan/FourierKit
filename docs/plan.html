goals, in order

  1. same accuracy as the reference. the output must match hugging face transformers running the original weights, exactly, on the three golden clips.
  2. highest throughput, highest speed, lowest latency. only exact paths compete. the cpu, gpu and neural engine (npu) are only means to that.
  3. three modes: transcribe (a file), record (capture, then transcribe), listen (live text while you speak).
  4. great defaults, everything exposed. it works with zero config, and every knob is public.
  5. a mac app in native swiftui with liquid glass, dark only, for macos 26 or later.

rules

  • weights: only the native transformers checkpoint, bf16, 4.08 gb, unchanged, pinned to revision 8c2a8871f1304aa2f634da4fb95e24438c4945b9 and hash-checked.
  • native and low level: swift and apple frameworks only (accelerate, core ml, metal). no third-party packages in the sdk or app.
  • external things are references only. nothing is copied and nothing becomes a dependency.
  • python lives in one place: a small harness that runs transformers to make the golden answers. it never ships.
  • nothing is set in stone. no chip, engine or trick is chosen in advance. the numbers choose.
  • npu or gpu, whichever is faster. the encoder is raced on both. the decoder starts on the gpu, and a one-layer benchmark tests the npu and cpu before either gets a full build. the npu wins a tie, and accuracy is never traded for it.
  • the cpu does what is parallel. it runs work that splits across cores, plus logic the other chips cannot do. small audio stages stay on it in 32-bit, and anywhere the cpu is the slow part, that work moves to the npu or gpu.
  • the main thread is never touched. all model, audio and file work runs in the background, so the ui never waits on it.
  • measure, don't assume. only a trace proves where something ran.
  • license: the engine, sdk and app are cc by-nc 4.0, the same as the weights. all of it is non-commercial and requires attribution.
  • all lowercase. every piece of text the app renders is lowercase, including labels, menus, errors and transcripts, and so is all doc prose. code identifiers, paths, urls and license text keep their case.
  • lowercase is display only. the sdk returns the model's exact text, so the golden test still compares true output. copy and export also keep the exact text.

how we work

the mindset: hill-climb everything. nobody needs to know the final design up front. we need a direction, a score and a fast loop. attempts are cheap, a failed attempt is information, and only a measured gain moves us uphill.

the loop:

  1. pick one number with a concrete target, such as "make encoder blocks 2x faster", never just "optimize".
  2. start from the current best, with its score on record.
  3. make one bet, with a stated reason it should help.
  4. try it in a fresh agent in its own git worktree.
  5. run the golden test. accuracy first, speed second.
  6. keep it or drop it. keep only if it is exact and beats noise. log the result either way.
  7. climb again from the new best.

getting off a local peak: when small bets stop paying, run a few big jumps in parallel, such as another engine, another chip split or a clean rewrite of one stage. a jump can look worse at first, so it gets a short budget to climb before it is judged.

the orchestrator is fable. it owns the goal, the scoreboard and the next bets. it spawns subagents, hands each a short brief with one target, and lands only work that passes the golden test. it stays out of bulk implementation so its context stays clean.

subagents are spawned as needed. use the cheapest model likely to get the job done, and move up when it fails.

modeluse it for
haikusearching, reading logs, mechanical edits, running and summarizing golden runs
sonnetroutine implementation, harness work, app ui
opushard implementation: metal, core ml conversion, concurrency, the decoder
fableorchestration, architecture, numeric mismatches and problems others could not solve

swarm rules:

  • one agent, one question, one worktree. parallel work never shares files.
  • timing runs go one at a time. agents can build and explore in parallel, but a speed or energy number only counts from a quiet machine. golden runs go through one queue.
  • fresh context beats a long thread. after about five rounds of back and forth, or two failed fixes, stop and restart with the lessons and the errors.
  • state lives in the repo, not in chat. the scoreboard and every try go in docs/performance.html, so any new agent can pick up from there.
  • agents cannot move the goalposts. no agent may edit the golden set, loosen the golden test or change how it measures to get a win. those changes need the owner.
  • show the climb. speed and accuracy are plotted over time like a loss curve, with each stage measured end to end.
  • one test, no others. agents do not write unit tests or new test suites. time goes into the engine and the golden test.
  • the owner stays on decisions. goals, license, going public, and anything hard to undo come back as one clear question at a time.

what we take from the two posts:

  • effective swarm riding for engineers by georgios konstantopoulos: short prompts with concrete targets, tune the environment, differential testing against a reference, no unit tests, no ci, measure every component, a monorepo with few dependencies, and let the swarm run while the human gets out of the way.
  • you're vibe coding wrong by edward ahn: building is search, failed attempts are information, restart often to avoid context rot, carry lessons forward, and treat a clean one-shot as a sign the problem is understood.

what we deliberately do not take: deleting docs/, removing all comments, or skipping orchestration. this project runs long and is meant to go public, so it keeps its measurement log and a light orchestrator.

the model

confirmed from its source code.

melwhisper-style log-mel, 128 bins, 10 ms hop, any length

encoder24 layers, 314m params. attention only sees its own 8-second block
projectorlinear, gelu, linear

why the blocks matter: fixed 1-second and 8-second blocks can run in parallel. the mel floor comes from the loudest point in the clip, so a cached block stays valid only until a louder frame raises that floor.

placement: an open search

every stage is built so it can run on more than one chip. the best mix is found by testing, and it can differ by task.

how a placement wins, in order:

  1. it is exact. it passes the golden test, or it is out.
  2. it wins the number that matters for the task. highest throughput for batches, highest speed for a single file, lowest latency for live text.
  3. on a tie, the npu wins. a tie means within measurement noise, and the npu usually uses less power and leaves the gpu free.

effort goes where the time is. the full diagram of how each step is packed is in the architecture page.

what gets tried:

  • each model stage on each chip, in the one-layer benchmark before any full build.
  • mixes: for example npu encoder with gpu decoder, all gpu, or all npu.
  • overlap: one chip prepares the next piece while another decodes the current batch.
  • different ways to run the same chip: mpsgraph and hand-written metal on the gpu, accelerate on the cpu, and core ml on the npu. the private neural engine api waits until after phase 9.

the best mix may differ by:

  • task: a long file wants throughput, live mode wants the shortest delay.
  • clip length: short clips are dominated by start-up cost, long ones by steady speed.
  • power: plugged in, on battery, or hot.

what ships: a placement table built from the measurements. automatic is the default and picks the fastest exact path for the task. npu is opt-in and uses the npu at every stage where it passes the golden test, even if another chip is faster. efficiency is opt-in and favors lower power. any stage can be pinned by hand.

starting hunches, to be tested, not trusted: other projects report decoders this size run faster on the gpu than the npu, and encoders run about equally on both. the npu usually wins on power.

the decoder is limited by memory bandwidth. each step reads about 3.4 gb of weights stored in 16-bit, or 6.9 gb stored in 32-bit. the gpu on this mac measured about 91 gb/s of memory reads, which caps a single stream near 26 or 13 steps per second. the cost comes from how weights are stored, so 32-bit math can still run at the 16-bit ceiling. the exact path keeps a 32-bit cache, about 229 kb per context token, or about 0.46 gb per step for a 2-minute piece. this shapes the design:

  • batched beams are the base design, sharing one audio prefix cache, because a batch reads the weights once per step.
  • pieces share one continuous batch, and a finished piece hands its slot to the next.
  • the decoder is not split across chips, since they share the same memory.
  • before writing converters, a one-layer benchmark on each chip measures the real ceiling. it sweeps batch width and context length, measures prefill speed, and tests 16-bit weights with 32-bit math. it is phase 0.
  • long audio prefers shorter pieces, which cut both cache reads and prefill.

the combined engine

the decoder is the center of the design. a 2-minute clip needs about 15 encoder blocks but about 410 decoder steps, and the decoder reads roughly 2,000x more weight data. the full diagrams are in the architecture page.

  • store 16-bit, compute 32-bit. weights are read at half the memory cost, and the math keeps full precision.
  • one wide decoder batch on the fastest chip. beams and pieces share each weight read.
  • refill slots at once. when a piece ends, the next one takes its slot without draining the batch.
  • the encoder works ahead on the other chip. this helps across pieces, because inside one clip the decoder needs all the audio tokens before it starts.
  • never copy beam history. each step writes to its own cache slot, and a per-beam ancestry table says which slots make up each beam.
  • batching must be invisible. a row's scores are bit-identical at any batch width, slot, neighbor or padding, with metal fast-math off.
  • pack the calls. many pieces go into one gpu command buffer or one npu batch, and the next call is prepared while this one runs.
  • slow down, never overflow. bounded queues hold back the stage before a slow one.
  • recover on its own. if a chip call fails, that piece reruns on the exact gpu path.

build order: run the one-layer benchmark, build batched beams on the full 32-bit path, add the beam ancestry cache, switch to 16-bit weights with 32-bit math, widen the batch, race the encoder and move it ahead, test pure 16-bit math, then turn on the scheduler.

the sdk packs itself for the workload. it reads what it was given and how busy the machine is, then re-plans before every decoder step. automatic needs no configuration, and every choice can still be pinned by hand.

the engine

  • a swift converter reads the safetensors file and builds what each chip needs, once, on this machine.
  • weights stay exact. the default keeps the raw bf16 bits and expands them to 32-bit inside the kernel, so every value is exact. paths using apple's float16 count any values that do not fit.
  • the first path is full 32-bit on the gpu with mpsgraph, so logic bugs are separated from precision bugs.
  • the fast default stores 16-bit and computes 32-bit, with a 32-bit cache. it uses a hand-written metal kernel unless the benchmark shows mpsgraph can do this without a 32-bit weight copy.
  • core ml is the npu path, starting with the encoder, using fixed 104-token windows and a mask. with no packages, its model format has to be written by hand, so the npu decoder is built only if the one-layer benchmark shows it can win.
  • precision is the main accuracy risk. the default is 16-bit weights with 32-bit math. pure 16-bit math, including anything on the npu, must also pass the safety margin. weights that do not fit in 16-bit, or a stage that still fails, use the full 32-bit fallback.
  • no weight compression at first. the source checkpoint is never changed. a compressed copy is tried last, and kept only if it passes the golden test.

threads: the main thread stays free

the rule: the main thread only draws the ui. no stage in this plan runs on it.

workwhere it runs
uimain thread, drawing only
microphone callbackthe realtime audio thread. it only copies samples into a lock-free ring buffer, with no locks, allocation or waiting
audio decode, resample, melbackground pipeline
npu, gpu and cpu inferencebackground pipeline, one owner per chip, waiting on chips without blocking a thread
beam search and textbackground pipeline
download, convert, load, warm-uplow-priority background work, with progress
file reads, exports, measurement logsbackground
  • stages are connected by bounded queues. a slow stage slows the stage before it and cannot pile up memory. the microphone buffer is sized so audio is not dropped.
  • the ui gets at most one text update per frame. the pipeline coalesces changes, and the main actor only applies the newest one.
  • the sdk is safe to call from the main actor. every heavy api is async and leaves the main actor at once. events are produced off the main actor, and the app hops over only to draw.
  • live work has top priority. batch work yields to it, and cancel stops work at the next stage boundary.

accuracy

the holy grail: one golden test, three audio clips, many dimensions. there are no unit tests, no ci and no other test suites. if the golden test is right, the engine is right.

  • the reference: transformers at one pinned commit, running the pinned checkpoint on the cpu in 32-bit float, with a batch of one, apply_transcription_request(language="en"), no system prompt and the model's generation defaults.
  • the output format: token ids are the main comparison. final text uses return_format="transcription_only", so the sdk ports its repetition fix.
  • where the contract starts: 16 khz mono float32 samples. file decoding and resampling are outside it, because apple's and python's will not match bit for bit.
  • golden clips: three fixed clips, short (about 3 s), medium (about 11 s) and long (about 2 minutes). the long clip is at most 120 s. each must reach a stop token under the model's 512-token limit, so the reference is complete and never chunked. a clip is rejected if its own closest beam comparison sits inside 32-bit noise, checked with a float64 run.
  • what exact covers: the claim is identical output on these clips. audio too long for one pass is split, which changes the model's input, so it is not claimed identical to a single reference pass.
  • the golden reference set, saved once and then frozen:
    • the three clips as 16 khz mono float32, with their hashes.
    • the checkpoint revision and hash, the transformers version and every setting used.
    • per clip: mel, encoder output, the top 9 accumulated candidates and every beam comparison at each step, token ids, raw text and final text.

must pass on all three clips. one miss and the change is out:

the app-hosted run. three golden dimensions need a real app and input device, so they run inside FourierPlayground:

  • main thread: no model work runs on it, and it never stalls for more than 8 ms.
  • noise: the three clips with room noise, played through a real input and voice processing, compared with the clean reference.
  • placement: MLComputePlan checks the planned chip at load, and an instruments trace proves where work ran.

when it fails, it says where. the saved mel, encoder output and step scores show the first stage that drifted. they are diagnostics, so only the final result decides pass or fail.

  • a change that fails the golden test is not kept, however fast it is.
  • there is always one exact path. if a fast 16-bit path cannot reproduce the reference, a slower 32-bit path that does is kept, and only exact paths can be defaults.

speed: the hill-climb

  • numbers tracked: audio seconds per wall second, time to first text, live draft and final delay, tokens per second, load time, memory, energy.
  • loop: change one thing, run the golden test, keep it only if it is faster and still correct. log every try, kept or dropped.
  • things to try: placement mixes, parallel encoder blocks, batched beams, batch width, slot refill, beam ancestry cache, scheduler thresholds, piece length, cache layout, 16-bit against 32-bit math per stage, shared memory between chips, weight compression last.
  • baselines to beat: transformers on this mac. the published 8-bit mlx build and q8 gguf are tracked as a separate, lower-precision class, because they are not exact.
  • how numbers are taken: release builds, a quiet machine in a nominal thermal state, cold and warm runs recorded apart, and the median of 5 repeats. a tie means within 3%.

what replaces a command line tool:

  • checking and measuring: one command, swift test -c release, runs the golden test and writes its dimensions to the measurement log. the app-hosted run covers the rest.
  • converting: the kit's prepare() downloads and converts the model, so no separate tool is needed.
  • trying it by hand: FourierPlayground.

why one repo:

  • the kit and the app change together while the engine is being tuned, so one commit keeps them in step.
  • the golden set and its test sit next to the code they check.
  • the kit is a clean swift package at the repo root, so any app can depend on it directly.

rules that keep it clean:

  • the app uses only the public api. if it needs something private, the api is missing a feature.
  • one core module, four folders. FourierKit is a single import, and FourierKitUI is optional. inside it, Speech uses Audio, Model and Text, and they never reach back up.
  • measuring code lives in the golden test, not in the kit.
  • the app is an xcode project, because it needs a microphone permission, an icon and signing.
  • weights and converted models are never in the repo. they are downloaded and built into the user's application support folder.
  • golden files: the three clips live in git. the large saved tensors live on a private github release, with their hashes in git.

prepare progress

prepare() reports one smooth value from 0 to 100%, covering everything from download to warm-up.

let preparing = Task { try await speech.prepare() }

for await progress in speech.prepareProgress {
    progress.fraction       // 0.0 to 1.0, never goes backward
    progress.stage          // current stage
    progress.bytesDone      // during download
    progress.bytesTotal
    progress.timeRemaining  // nil until it can be estimated
}

try await preparing.value
  • one shared run. calling prepare() twice joins the same work, and any number of observers can read its progress.
  • cancel keeps partial files. work stops when the last waiting caller cancels.
stageshare of the barwhere progress comes from
check disk and files~1%files checked
download~60%real bytes
verify hash~5%real bytes hashed
convert weights~20%real tensors written
compile for each chip~8%finished models, estimated in between
load~3%finished models
warm-up~3%finished warm-up runs

these shares are starting values, replaced by measured times from this mac.

  • it only moves forward. a retry or resumed download never makes the bar jump back. if the final hash fails, the bar holds while the file downloads again.
  • 100% means truly ready. it reaches 1.0 only after warm-up succeeds, so the first transcription can start immediately.
  • smooth but honest. updates are capped to one per frame and eased between real values. if a step stalls, the bar slows and holds below that stage's limit.
  • it resumes. finished stages count as complete, and a partial download continues from its last written byte, and the final sha256 checks the whole file.
  • a ready model finishes instantly. it goes straight to 1.0.
  • it stays off the main thread. the app only draws the latest value.
  • core ml compilation is estimated. it reports no progress while it runs, so that part of the bar uses past timings.

keeping the engine hot:

  • keepWarm is automatic. after prepare(), the model stays loaded and warm while the app is active.
  • warm never means listening. the microphone is open only during listen() or record().
  • it cools down on its own. after 5 idle minutes, under memory pressure, or when the mac is hot, it releases memory and warms again on next use.
  • apps can control it with speech.warm() and speech.cool().

permissions:

  • asked only when needed. the first listen() or record() requests the microphone, never app launch, and file transcription never asks.
  • denied is a clear state. the sdk reports it, says what to do, and can open the right system settings page.
  • setup mistakes are caught early. a missing NSMicrophoneUsageDescription or audio entitlement returns a clear error before the request.
  • apps can take over with permissions: .manual or their own handler.

the three modes

  • transcribe: audio up to 120 s runs in one pass and is never split, so it matches the reference path. longer audio is cut at quiet points by one deterministic splitter, each piece runs the exact path, and the pieces are joined. if a piece reaches 512 tokens without a stop token, it is split and decoded again, so text is never silently cut off. progress and cancel.
  • record: raw microphone capture with a live level, then the same path as transcribe.
  • listen: live text while you speak. it has its own section below.

listen, in detail

the model is not a streaming model, so live text is built on top of it.

how it works:

  • finished blocks are encoded once and cached. they are encoded again only if a louder frame raises the phrase's mel floor.
  • every short step, only the newest audio is encoded. settled tokens are prefilled, so only the unsettled tail is generated.
  • re-prefill has a budget. audio comes before text in the prompt, so when the current block changes, the text after it is recomputed. this could take 0.15-0.4 s, so the update rate follows measured step time.
  • text that agrees across two passes becomes settled. the rest is the draft.
  • a pause ends the phrase, settles all of it and resets the window, so cost stays flat.
  • the final: each phrase gets an exact pass in the background as soon as it closes, so finish() only waits for the last phrase. the result equals transcribe with the same split points. finalPass: .fullAudio runs one pass over everything instead, at about 20 s for 2 minutes.

promises the api makes:

  • settled text never changes. it only grows.
  • draft text can change or vanish on any update. it is always the newest guess for audio after the settled part.
  • drafts are optional. with drafts off, or when nothing is uncertain, the draft is empty and only settled text arrives.
  • settled + draft is always the best full text so far.
  • the final transcript from finish() comes from the exact passes. its wording can differ from the live text, and it is the one to save.

the schema:

let live = try await speech.listen()            // or speech.listen(options)

let ui = Task {
    for try await event in live.events {
        switch event {
        case .started:                    break // microphone is live
        case .level(let level):           break // input loudness, for a meter
        case .speechStarted:              break // voice detected
        case .update(let update):         break // new settled and draft text
        case .phraseEnded(let phrase):    break // a pause closed a phrase
        case .warning(let warning):       break // fell behind, input changed
        }
    }
}

// when the user stops:
let transcript = try await live.finish()        // stop, get the final text, end the stream
try await ui.value

// or, instead of finish():
live.cancel()                                   // stop, discard, end the stream

stream rules:

  • .level events are coalesced to the newest value. .update events are full snapshots, so a slow reader gets the newest one and memory stays bounded.
  • cancelling the task that reads events does not stop the session. only finish() or cancel() does.
  • the scheduler shares the model across jobs. a transcribe during listen uses spare batch slots, and live work goes first.
  • each job has its own handle with progress, result and cancel.
  • one engine per process. every Fourier instance shares the same 4 gb of weights.
  • all public types are Sendable.
struct LiveUpdate {
    var settled: String             // never changes, only grows
    var draft: String               // may change, may be empty
    var text: String                // settled + draft
    var newlySettled: String        // added since the last delivered update
    var phrases: [LivePhrase]       // text with start and end times, each settled or draft
    var audioTime: Duration         // how much audio has been heard
    var delay: Duration             // how far the text is behind the voice
}

goals: a first draft in about half a second, settled text soon after, no flicker in settled words, and no growing delay in a long session. if the machine falls behind, updates slow down before any audio is dropped, and a warning says so.

how it is checked:

  • the three golden clips are played in as if spoken, at real speed.
  • settled text must never be taken back.
  • the final transcript must equal transcribe with the same split points.
  • draft delay, settle delay and how often drafts change are logged.

what could go wrong

  • 16-bit math may change the text. known trouble spots are the norm layers and long sums. fix by moving that stage to 32-bit, or by proven rescaling.
  • exact match is hard for the fast paths. a tiny numeric difference can flip a close call between two tokens. the bar does not move: that path is fixed, or it loses its place to the exact 32-bit path.
  • cache bugs. another project's port of this model family gave wrong output at certain cache lengths. the golden clips run through every cache length up to their full token count.
  • the npu has size and shape limits. reports disagree on how large one piece can be, so the limit is found by testing.
  • more chips and engines mean more work. build the simplest path per chip first, and write custom metal only where the numbers say it pays.
  • greedy is not a speed lever. three batched beams share each weight read, so greedy should gain only about 10%. beam search is the reference default and stays.
  • first run is slow and large. a 4 gb download and a conversion, and all variants can pass 16 gb. prepare() checks disk space first, resumes downloads and verifies the sha256. cache everything after.
  • this mac has no fan. long runs can slow down as the air heats up, so speed is recorded both fresh and sustained.
  • silent fallback. core ml can move work to another chip without saying so, and it does not report this per call. check the plan at load, and prove placement with traces.

not known yet

  • which mix of chips wins each task on this m4.
  • whether 16-bit computation reproduces the reference text exactly.
  • whether apple's tools can read 16-bit weights into 32-bit math without a 32-bit copy.
  • real speed, energy and accuracy.
